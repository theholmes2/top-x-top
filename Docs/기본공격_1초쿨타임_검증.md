# 기본공격 1초 쿨타임 + 중앙 요청 — 2026-11-03

> 2026-11-05 갱신: 현재 실행 흐름은 [플레이_스폰_전투_검증.md](플레이_스폰_전투_검증.md)를 따른다. 아래는 당시 구현·검증 이력이다. 고정 EnemyState 생성, 타깃 보관 생성자, 풀·스폰의 Root 미연결 설명은 현재 실행 경로에 적용하지 않는다.
>
> 현재 API: `new SkillUseBrick(attack, cooldownMs, powerPermille)` → `TryUse(nowMs, currentTarget)`.
> 현재 Root는 풀·스폰을 타입 등록하고 시작 난이도·스폰 위치를 EntryPoint에 공급한다. 활성 개체는 등장 순서 List이고 전체 상한도 적용한다.


> 같은 날 후속: 중앙은 MonoBehaviour.Update 대신 ITickable로 전환했다. 최신 파일·등록·검증은 [ITickable_중앙갱신_검증.md](ITickable_중앙갱신_검증.md)를 따른다. 아래 Update/중앙 컴포넌트/4개참조 기록은 전환 전이다.

## 이번 요소

기본공격 정의를1000ms/위력1000(1배)로 변경하고, 요청 시각을 받는 순수 SkillUseBrick과 기존 중앙 Update를 연결했다. 첫 유효 요청은 즉시 실행한다. 그 뒤에는 마지막 성공 시각에서1000ms가 지나야 다시 성공한다. 기본공격이 자동으로 요청되는 경로까지만 구현했다.

- Assets/Scripts/Skill/SkillConfig.cs: 재사용 기본 쿨타임도1000ms로 바꾸고 설명을 현재 실행 흐름과 맞췄다.

VContainer가 없어 공식 UPM Git 태그1.19.0 패키지 하나를 설치했다. 패키지 설치는 Unity PackageManager.Client.Add로 수행했고 manifest/lock을 손으로 쓰지 않았다. 공식 출처: https://github.com/hadashiA/VContainer/releases/tag/1.19.0

Root에서 만든 상태·사용 객체를 VContainer에 등록하고 RegisterComponent로 중앙 컴포넌트의 Inject 메서드에 같은 객체를 공급한다. Unity 전역 검색·중앙의 SO 읽기/상태 생성·새 반복 Update/코루틴은 제품 코드에 넣지 않았다. 실제 씬 검사에서 주입된 객체와 컨테이너의 실행 객체가 동일함을 확인했다. 여기서 DI 채택은 성능 향상 수치나 소스 생성/Zero-GC 검증을 뜻하지 않는다.

## 호출과 수명

```csharp
// Root: SO를 Unity 밖 순수 숫자로 읽어 이 캐릭터/스킬의 상태를 만듭니다.
var attack = new AttackBrick(player);
var basicAttack = new SkillUseBrick(
    attack,
    slime,
    basicConfig.BaseCooldownMs,
    basicConfig.PowerPermille);

// 중앙 Update: 매 프레임 요청하지만 실제 성공 여부는 Brick이 판단합니다.
long nowMs = (long)(Time.timeAsDouble * 1000);
basicAttack.TryUse(nowMs);
```

실제 중앙 코드의1000은 이름 있는 MillisecondsPerSecond 상수다. Time.timeAsDouble은 timeScale/일시정지 영향을 받는 게임 시간이며 서버 UTC가 아니다. 초→정수ms 변환 시 소수점 이하를 버린다. 반복해서 소수 주기를 더하지 않는다. 프레임이 경계보다 늦으면 그 프레임에 한 번 성공하고 실제 성공 시각+쿨타임으로 다음 시각을 정한다. 과거의 밀린 공격을 while로 따라잡지 않는다.

SkillUseBrick 생성자는 (AttackBrick attack, CharacterState target, int cooldownMs, int powerPermille)이고 bool TryUse(long nowMs)를 제공한다. 쿨타임1~int.MaxValue, 위력0~int.MaxValue를 받는다. 음수 시각이나 다음 시각이 long에 담기지 않는 유효 요청은 피해 적용 전에 예외로 거절한다.

사용 가능한 시각인지 확인한 뒤 AttackBrick이 대상·생존을 검사하고 피해를 최대1회 적용한다. 효과 성공 후에만 NextUseAtMs를 갱신한다. 0피해도 성공이므로 소비하며 null/자기/사망 대상·사망 공격자 실패는 소비하지 않는다. 같은 시각/쿨타임 중 연타·시간 역행 요청은 성공시키지 않는다. 공격 횟수·누적횟수를 반환하지 않는다.

서로 다른 스킬은 같은 공격 효과/캐릭터를 사용해도 SkillUseBrick 인스턴스와 다음 시각이 별개다. 같은 SO를 두 캐릭터가 사용해도 시각이 공유되지 않는다. 버프 효과 자체는 아직 없으며 버프 구현/공통 효과 계층을 선행하지 않았다.

이번 실행 객체의 대상은 생성자에 연결한 슬라임 하나다. 동적 타깃 교체/재출현은 이번에 넣지 않았다. AttackBrick 자체의 요청별 타깃/현재 스탯 사용은 유지된다. 현재 단계의 정의 수치는 Root 생성 시 읽으며 실행 중 SO 변경을 실시간 반영하는 기능도 만들지 않았다. Scene Scope가 끝나면 해당 상태/실행 객체의 소유권도 끝난다. SO에는 사용 시각을 쓰지 않는다.

## 검증

실행 중인 새 top x top Unity Editor6000.3.19f1에서 최신 코드 컴파일 실패false·컴파일 중false·최신 콘솔 오류0을 확인했다. CLI success만 보고 판정하지 않고 실제 메서드/Root/상태를 호출했다.

쿨타임 단독25개 PASS:
- 실제 기본1000ms/1배·강타 기존1000ms/2배 데이터.
- 최초0 즉시 성공/다음1000, 같은0·999 거절,1000 성공, 경계 반복/1999 연타 거절.
- 10000으로 건너뛰어도 공격1회/다음11000만 갱신.
- 다른 스킬·다른 캐릭터의 독립 시각.
- null/자기/사망 대상·사망 공격자의 실패 미소비, 이후 같은 시각 유효 상태가 되면 성공.
- 0피해·0위력 성공도 쿨타임 소비.
- 음수 시각/잘못된 생성 수치/null효과와 long 최대 시각의 오버플로/피해 미변경.
- 실행 뒤 SO의 JSON 내용과 dirty 상태 불변.

기존 AttackBrick 효과21개도 현재 Config 데이터로 재검사하여 PASS했다. 1배8·2배16,0피해,초과 피해 실제HP감소량,사망/null/자기검사,현재공격/방어력,배율반올림·곱셈오버플로가 포함된다. 이 중 직접 TryAttack를 두 번 호출하는 검사는 **효과만** 검증한다. AttackBrick이 쿨타임을 담당한다는 뜻이 아니며, 실제 중앙 사용 경로는 SkillUseBrick을 거친다.

실제 Scene/Play 확인:
- 씬 Root에서 생성한 실행 객체가 중앙에 동일하게 주입됐다.
- 관찰 중2746프레임 진행. 관찰 시작 전 메모리 HP만 한 번45로 복원했다. 이 조작은 검사 준비이며 체력 재생 기능이 아니다.
- HP45→37→29→21→13→5→0.
- 기록된 실제 성공ms:1001,2002,3002,4003,5004,6004. 간격1000~1001ms.
- 매 성공 시 NextUseAtMs는 성공시각+1000이었다. 사망 이후 HP0·다음 시각이 유지됐으며 플레이어 HP도 유지됐다.
- 최초 요청 즉시 정책은 단독0ms 경계로 확인했다. Play 기록은 관찰 준비 이후 구간이며 첫 프레임 전체 기록으로 과장하지 않는다.
- 검증 후 Play를 종료하고 임시 runInBackground 값을 원복했다. 검사 객체는 메모리에만 있었고 영구 테스트 CS를 추가하지 않았다.

## 범위 밖

아트·Animator·후딜·HP UI·VM/R3·이벤트 버스·강타 Scene 연결·마나·큐/슬롯·적 반격·재출현·실제 재생·성장/저장·서버 정산은 추가하지 않았다. 애니메이션 완료를 판정 조건으로 삼지 않는다. 현재 화면에 전투 UI는 없으며 상태 인스턴스로만 동작을 관찰한다. 이 단계가 완성 게임·서버 권위 검증은 아니다.

커밋·Push·PR·클라우드 배포·이전 top of top 변경 없음. 기존 사용자 변경을 보존했다. Unity가 생성한 Scene의 빈 직렬화 필드에는 일부 trailing space가 있어 전체 git diff --check의 형식 경고와 기능 검사 결과를 구분한다. 코드 설명 채팅에 이번 변경을 읽기 전용 학습으로 전달하고 다음 기능은 검토 전 진행하지 않는다.
