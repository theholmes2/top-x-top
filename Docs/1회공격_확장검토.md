# 1회 공격과 요청 정책의 분리 — 2026-11-02

> 후속: 같은 날 스킬 정의 데이터와 위력 입력을 추가했다. 최신 호출 및 구현/미구현 범위는 [스킬정의_기본공격_검증.md](스킬정의_기본공격_검증.md)를 따른다. 아래는 이전 1회 공격 단계의 기록이다.

## 이번 변경

AutoAttackBrick을 AttackBrick으로 바꿨다. 공격자는 생성자로 받고 대상은 매 요청에 받는다. TryAttack(target, out appliedDamage)는 대상 유효성·양쪽 생존을 확인하고 피해를 한 번 적용한다. 반환값은 횟수가 아닌 실행 성공 여부다.

- 피해 공식은 max(0, 공격력 - 방어력).
- 0 피해도 실행 성공이며 애니메이션 요청 대상이 될 수 있다.
- 실제 피해 반환은 적용 전 HP - 적용 후 HP다. HP5인 적에게 계산 피해8을 주면 반환은5다.
- 사망·null·자기 자신을 대상으로 하는 요청은 상태 변경 없이 false를 반환한다.
- 공격 간격·현재 시간·반복·밀린 공격·프레임당 처리 횟수는 제거했다.
- 파일 이동은 Unity AssetDatabase로 수행하여 meta/GUID를 유지했다.
- 중앙 Update·VContainer·Scene·화면·스킬 정의·서버는 연결하지 않았다.

## 확장할 때의 역할

수동 입력 / 자동 요청 정책 / 예약 큐
→ 공통 스킬 사용 처리
→ 대상·생존·쿨타임·자원 등 사용 가능 여부 확인
→ 1회 효과 적용 및 사용 확정
→ 로컬 사용 결과를 표현·기록에 전달

현재 AttackBrick은 이 중 단일 대상 일반 공격 효과와 최소 유효성 검사만 담당한다. 스킬 사용 가능 조건 전체를 구현한 것으로 취급하지 않는다.

### 자동사용과 수동사용

언제 요청할지는 별도 정책이다. 중앙 Update가 자동 요청 담당에 시간을 전달하고, 수동 입력은 같은 스킬 사용 경로에 직접 요청하면 된다. 쿨타임 검사를 자동 요청 담당에만 두면 수동 요청이 우회할 수 있으므로 실제 사용 가능 여부는 공통 사용 경로에서 검사해야 한다. 아직 그 코드는 만들지 않았다.

### 예약 큐

큐가 다음 예약 하나를 꺼내 같은 사용 경로에 요청할 수 있다. 예약 취소는 큐에서 처리하고, 현재 공격 Brick은 큐를 알 필요가 없다. 예약10개·장착5개·자동 최소5초는 검토된 후보이며 이번 변경으로 확정·구현하지 않는다. 꽉 찬 큐·실패한 예약·재시도·쿨타임 시작점은 정책 확정 후 적용한다.

### 스킬별 간격·위력·효과

정의는 스킬 Config, 사용 시각은 스킬별 실행 상태, 실제 효과는 필요한 계산이 맡는 방향이 가능하다. 현재 공격자는 상태 참조 하나를 공유하므로 현재 공격력 변경을 다음 요청에서 읽고, 서로 다른 적을 요청 시 전달할 수 있다. 강타 배율·버프·회복을 기존 일반 공격 공식에 이름만 바꿔 억지로 넣지는 않는다. 실제 두 번째 효과가 승인될 때 공통 사용 흐름과 필요한 차이만 분리한다. 아직 스킬 인터페이스·효과 계층을 선행 구현하지 않는다.

### 애니메이션과 결과

성공한 스킬 사용 한 번을 기준으로 로컬 표현 신호를 보낸다. AttackBrick은 Animator·DOTween·Unity View를 직접 참조하지 않는다. 0 피해 성공과 실행 거절을 구분한다. 후딜 모션은 다음 유효 공격으로 취소 가능하며 이전 애니메이션 완료를 공격 승인 조건으로 삼지 않는다.

광역기가 여러 대상에게 피해를 줘도 스킬 사용은1회다. 향후 '스킬 사용 신호'와 '대상별 피해 결과'를 구분해야 타격 수만큼 공격 애니메이션을 중복 시작하지 않는다. 현재는 단일 대상만 구현했다.

### 기록과 서버 검증

로컬 사용·처치 결과와 서버가 정산 확정한 사실은 다르다. 실행 결과로 필요한 로컬 기록을 만들고, 서버 확정 사실 방송은 이후 정산 경로에서 처리한다. 이번 bool/out 반환만으로 구간 기록이나 중복 정산 방지가 구현됐다고 설명하지 않는다.

## 의도적으로 보류한 사항

실제 스킬 정의, 쿨타임·마나, 자동사용 정책, 요청 큐, 여러 행동의 시간순 처리, 애니메이션 연결, 처치·스킬 결과 이벤트 형식, DI와 Scene 조립은 다음 요소 검토 범위다. 한 요청당 한 효과 적용이라는 경계만 먼저 구현했다. 이 구조는 해당 기능을 추가할 연결 방향을 제공하지만 나중에 코드를 전혀 바꾸지 않아도 된다는 보장은 아니다.
