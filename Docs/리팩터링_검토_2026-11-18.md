## 2. 이번 리팩터링에서 보존할 동작

- 첫 스폰은 즉시, 이후 정기 스폰은 한 Tick 최대 한 마리다. 정기 시간표 변경은 R09로 따로 다룬다.
- **매 처치 보충으로 되돌리지 않는다.** 사망 처리 성공 후 활성 적이 0마리일 때만 즉시 한 마리 보충하고 정기 스폰 일정은 건드리지 않는다.
- 전체 상한·종류별 상한·수량 순환과 FIFO는 그대로다. 전체 상한이 종류별 합계보다 커도 정상이다.
- 적이 없으면 우측 진입, 적이 있으면 현재 마지막 적 바로 뒤에 페이드인한다. 첫 타격 전에는 페이드를 끝낸다.
- 이동한 실제 거리로 배경·사망 연출 개체·기존 잔상을 함께 민다. 대시 구간은 가속하고 후딜 중에는 이동을 멈춘다.
- 예약 선딜 중 HP를 깎지 않는다. 도착·예약 시각·쿨타임·동일 State를 확인한 Tick에 한 번 타격한다.
- 접촉 자세, HP 갱신, Hurt 또는 Death가 같은 타격 Tick에 이어진다. 피해는 Animator 완료 여부에 의존하지 않는다.
- 실제 성공한 타격부터 공통 후딜을 끝까지 지킨다. 후딜 중 스폰·쿨타임·페이드·사망 수명은 계속 갱신한다.
- 모션 순번은 성공한 타격에서만 1→2→3→1로 진행하며 새 대상은 1부터다. 압축 선딜은 잔상, 시간 부족은 스킵 정책을 유지한다.
- 새 EnemyState가 각 대여를 구분한다. 오래된 타격 예약·피격 구독·사망 처리가 재대여 개체에 적용되지 않아야 한다.
- R3 체력 ViewModel은 초기 값을 즉시 전달하고, 반환 시 View 구독과 State 구독을 해제한다.

### R02. 실패 도중 실행 상태가 갈라지는 경로

**A. HP 변경 통지가 쿨타임 확정보다 앞선다**

[CharacterState.ChangeHp](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Character/CharacterState.cs:38>)는 HP를 먼저 바꾼 뒤 `HpChanged`를 동기 호출한다. 그 이후 [AttackBrick](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Combat/AttackBrick.cs:67>)이 실제 피해량을 돌려주고 [SkillUseBrick](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Skill/SkillUseBrick.cs:90>)이 쿨타임을 확정한다.

따라서 구독자가 예외를 던지면 HP만 변하고 쿨타임/후딜/사망 처리는 확정되지 않을 수 있다. 살아 있는 적이면 다음 Tick에 추가 타격될 수 있고, 죽은 적이면 활성 계수가 남을 수 있다. **예외를 주입해 실행한 결과는 아니며 호출 순서로 확인한 조건부 위험**이다.

**B. 표현 호출과 반환 중 예외도 상태 정리를 끊을 수 있다**

- [CommitStrike](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Simulation/SimulationTickGlue.cs:297>)의 `ShowRecovery`는 `TryUse`보다 먼저 호출된다. 이 표현 호출이 실패하면 전투 자체가 중단될 수 있다.
- [EnemyPoolGlue.TryReturn](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Enemy/EnemyPoolGlue.cs:95>)은 먼저 `rented.Remove`를 한 뒤 Unbind/표시 초기화/반환 스택 추가를 한다. 표시 초기화가 예외를 던지면 대여 집합에서도 빠지고 반환 스택에도 없는 상태가 된다.
- [TrySpawn의 catch](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Enemy/EnemySpawnGlue.cs:209>)는 `pool.TryReturn` 이후에 계수를 해제한다. 반환이 예외면 계수 해제를 놓친다. 예를 들어 StatsConfig만 있고 본체 Renderer가 없는 프리팹은 현 Difficulty 검증을 통과할 수 있고, SetDisplayOrder에서 이 경로로 진입할 수 있다.
- [TryBeginDeath](<E:/GameDev/unity-main-portfolio/top x top/Assets/Scripts/Enemy/EnemySpawnGlue.cs:321>)도 점유 해제 후 연출 호출이 실패하면 dying 등록/반환을 놓칠 수 있다.

**변경 방법**

1. 피해/실제 피해량/쿨타임/후딜 확정과 외부 표시 통지 사이의 경계를 명시한다. 같은 Tick의 표시 순서는 보존하되 외부 구독/Animator 예외로 이미 확정한 게임 상태가 반쯤 남지 않게 한다.
2. HP 변경은 최종 값 한 쌍으로 계속 통지한다. 확정 후 통지 단계로 옮기거나 관찰자별 실패를 보고하고 격리하는 방식 중 하나를 정해 단일 호출 경로로 구현한다. 임의로 쿨타임만 선소비해 실패 공격까지 소비하도록 바꾸지 않는다.
3. 반환 준비 실패 시에도 소유권 추적은 유지하고, 성공한 반환에만 대여 제거를 확정한다. 복구할 수 없는 개체의 파괴/원본 목록 정리는 풀 소유자 한 곳에서 맡는다.
4. 스폰 실패 시 점유 해제는 반환 실패와 독립적으로 보장하고, 사망 연출 실패 시에는 안전한 즉시 반환 경로를 둔다. 예외를 조용히 삼키지 말고 원인을 남긴다.

**분리 예시 코드**

아래는 수명 부분의 설명용 예시다. 완성 구현이 아니며 생성 간격도 같은 계산 책임으로 함께 정리한다. lifetime이 유한한 양수이고 elapsedSeconds가 유한한 0 이상이라는 입력 계약을 Config/호출 경계에서 보장해야 한다.

```csharp
using System;

/// <summary>잔상 수명과 표시값을 개체별 상태 저장 없이 계산합니다.</summary>
public sealed class DashGhostTrailBrick
{
    /// <summary>다음 수명과 현재 알파 및 표시 여부를 제공합니다.</summary>
    public (float Remaining, float Alpha, bool Visible) CalculateLife(
        float remaining,
        float initialAlpha,
        float lifetime,
        float elapsedSeconds)
    {
        float nextRemaining = Math.Max(0f, remaining - elapsedSeconds);
        float nextAlpha = initialAlpha * (nextRemaining / lifetime);

        return (nextRemaining, nextAlpha, nextRemaining > 0f);
    }
}
```

Glue에서 결과를 적용하는 형태다. `settings`는 SO에서 공급할 순수 값의 예시 이름이다.

```csharp
var result = calculation.CalculateLife(
    ghost.Remaining,
    ghost.Alpha,
    settings.Lifetime,
    seconds);

ghost.Remaining = result.Remaining;
ghost.Renderer.transform.position += Vector3.left * distance;

Color color = ghost.Renderer.color;
color.a = result.Alpha;
ghost.Renderer.color = color;
ghost.Renderer.enabled = result.Visible;
```

### R04. EnemySpawnGlue의 순환·배치 정책

## 6. 개발 요청으로 옮길 때의 순서

1. 기존 동작 표를 고정하고 R02의 예외 일관성과 R01의 전투 시간 경계를 먼저 정한다. 핵심 실행 시각을 작은 입력 표로 검증한다.
2. 잔상 R03을 하나의 작은 완성 사례로 진행한다. Config→순수값→상태 없는 Brick→개체별 Glue 흐름을 확인한다.
3. R04 스폰 순환/배치, R05 페이드, R06 배경을 각각 검토 가능한 크기로 진행한다. 이 단계에서 R07 설정 이전도 해당 기능과 함께 수행한다.
4. R08 필수 참조와 R10 설명을 관련 파일 변경에 묶는다. 전체 프로젝트 포매팅 변경을 섞지 않는다.
5. R09는 별도 정책 변경으로 검증하고, 처음 기준점·지연·장시간·상한 실패·long 경계·전멸 보충을 확인한다.
6. 각 단계 완료마다 실제 파일과 검증 결과를 코드설명→CS 구조도로 전달한다. UML의 변수/메서드·한국어 설명과 실행 흐름을 함께 갱신한다.

## 7. 검토 범위와 완료 판정

이번에 수행한 것은 소스·설정·기존 자료의 읽기 검토와 이 문서 작성이다. Unity 플레이, 최신 컴파일, 빌드, 예외 주입, 성능 측정, 외부 서비스 검증은 실행하지 않았다. R02는 소스로 경로를 확인한 조건부 위험이며 실제 현재 프리팹이 깨졌다고 단정하지 않는다.

리팩터링 구현의 완료 기준은 최신 컴파일, 순수 Brick의 관련 경계 입력 검사, 실제 씬의 타격/후딜/스폰/줄 이동/R3 대여 수명 검사, 필수 프리팹·Config 참조 연결과 GUID 보존, 사용자가 읽을 수 있는 변경 설명이다. 과거 Docs 자료는 해당 날짜의 증거로만 활용하고 최신 통과 기록으로 대체하지 않는다.

게임 코드·씬·에셋·패키지·기존 문서는 이 검토에서 변경하지 않는다. 개발 채팅 전달은 사용자가 문서를 확인한 뒤 별도 요청한 범위로 진행한다.
