# 몬스터 프리팹·풀·스폰 API 검증 — 2026-11-04

> 2026-11-05 갱신: 현재 실행 흐름은 [플레이_스폰_전투_검증.md](플레이_스폰_전투_검증.md)를 따른다. 아래는 당시 구현·검증 이력이다. 고정 EnemyState 생성, 타깃 보관 생성자, 풀·스폰의 Root 미연결 설명은 현재 실행 경로에 적용하지 않는다.
>
> 현재 API: `new SkillUseBrick(attack, cooldownMs, powerPermille)` → `TryUse(nowMs, currentTarget)`.
> 현재 Root는 풀·스폰을 타입 등록하고 시작 난이도·스폰 위치를 EntryPoint에 공급한다. 활성 개체는 등장 순서 List이고 전체 상한도 적용한다.


대상: E:/GameDev/unity-main-portfolio/top x top. 현재 수치와 외형은 임시 초안이다.

## 구성과 선택 이유

- EnemyGlue: Inspector의 StatsConfig 원본을 읽어 InitializeState에서 새 EnemyState를 만든다. OnEnable 자동 초기화가 없다. State는 전투가 같은 참조로 읽도록 제공한다.
- DifficultyConfig / EnemySpawnEntry: EnemyGlue 프리팹과 MaxSpawnCount를 직접 지정한다. 별도 카탈로그·팩토리 없이 종류별 동시 상한을 표현한다. 같은 프리팹 중복 항목은 상한 우회를 막기 위해 거부한다.
- EnemyPoolGlue: VContainer IObjectResolver를 생성자 주입받는다. 부족할 때 resolver.Instantiate로 생성·주입한다. 빈 DI 인터페이스나 Glue 주입 메서드를 만들지 않았다. 프리팹별 반환 스택, 원본 대응, 대여 집합으로 재사용·소유권을 관리한다.
- SpawnCountBrick: Unity·DI 없이 종류별 상한과 점유 수를 복사·판정한다. Config 변경이 실행 중 계수를 바꾸지 않는다.
- EnemySpawnGlue: 풀을 생성자로 주입받고 Configure로 난이도를 받는다. TrySpawn은 개수 점유 → 비활성 대여 → 새 State 초기화 → 위치 지정 → 활성화 순서다. 실패 시 점유를 되돌린다. TryDespawn은 반환 성공 후 개수를 줄인다.
- 실제 오브젝트를 다루는 풀·스폰은 Glue, 정수 개수 판정은 Brick이다. 서비스는 VContainer 등록 가능한 일반 클래스지만 현재 씬 Root에는 등록하지 않았다.

## 사용 경계

- 난이도 1: 슬라임 1 / 2: 슬라임 2·쥐 1 / 3: 쥐 2·고블린 1 / 4: 고블린 2·늑대 2 / 5: 늑대 3·골렘 2.
- 숫자는 종류별 동시 존재 상한이다. 누적 생성 횟수·반드시 채울 수량이 아니다. Configure만으로 생성하지 않는다.
- TrySpawn으로 얻은 개체는 반드시 같은 EnemySpawnGlue.TryDespawn으로 반환한다. 직접 pool.TryReturn하거나 외부 Destroy하면 스폰 담당의 계수를 우회한다. 자동 외부 파괴 감지·사망 처리는 이번 범위가 아니다.
- 활성 개체가 있으면 Configure를 거부한다. 자동 난이도 전환이 아니다. 한 난이도 실행은 한 스폰 담당이 소유하며 여러 담당의 전역 합산 상한은 구현하지 않았다.
- 반환 보관 수와 스폰 상한은 별개다. 필요 시 추가 생성하며 캐시 제거·사전 생성 정책은 없다.
- EnemySpawnGlue.Dispose는 자신의 활성 개체를 반환한다. EnemyPoolGlue.Dispose는 대여·보관 개체 모두 정리한다. 최종 소유자는 반드시 Dispose해야 하며 향후 Scope에서 관리한다. 종료 후 요청은 거부한다.
- 반환 시 실제 변경하는 root 활성 상태·위치·회전·스케일·State 참조만 복원한다. Body Sprite는 프리팹 고정값이며 런타임에 교체하지 않는다.
- 기존 BindState는 유지하지만 풀 대여는 InitializeState를 사용한다. 직접 BindState/InitializeState 호출로 대여 중 상태를 교체하는 것은 이 실행 흐름에 포함하지 않는다.

## 검증

Unity 6000.3.19f1, 연결된 Editor CLI 사용. 최신 스크립트 재컴파일 완료, compilationFailed=false. 영구 테스트 CS나 씬을 추가하지 않고 CLI 메모리 코드와 임시 additive 씬으로 검사했다. 202개 assertion 통과.

- 5종: 루트 Transform+EnemyGlue, Body Transform+SpriteRenderer, StatsConfig·Sprite 참조, 초기 State=null.
- 실제 풀 대여는 비활성이고 기본 HP 상태가 연결된다. 피해 후 반환·재대여에서 GameObject는 같고 State는 다르며 기본 HP로 복원된다. 이전 State와 Config는 변하지 않는다.
- 중복 반환·다른 풀 반환 거부, 위치 복원, 프리팹별 보관 분리.
- 난이도 1~5의 기존 숫자와 실제 프리팹 대응, 종류별 상한까지 성공·다음 요청 거부, 반환 후 같은 자리 재스폰, 미등록 종류 거부.
- 활성 개체 보유 중 재설정 거부, VContainer 생성자 주입으로 풀·스폰 조립 성공.
- Dispose 반복 호출 안전, 활성 개체 반환 및 풀 전체 제거, 종료 후 요청 거부.
- 테스트 종료 후 기존 SampleScene 활성 복원, dirty 상태 동일. 플레이모드는 실행하지 않았다.

5개 난이도 에셋과 기존 슬라임 프리팹은 Unity API로 기존 경로에 저장하여 meta/GUID를 유지했다. StatsConfig 참조를 프리팹 참조로 실제 매핑했고 기존 수량을 확인한 뒤 저장했다. 이전 프로젝트는 읽기 전용으로 다뤘다.

## 미연결·한계

Root·중앙 Tick·공격 대상은 변경하지 않았다. 현재 기존 전투의 EnemyState와 새 프리팹 State는 아직 연결되지 않는다. 플레이 시작 자동 실행·사망·보상·자동 반환·자동 리스폰·UI·서버는 구현하지 않았다. R3·이벤트 버스·DOTween도 이번 역할에 강제하지 않았다. VContainer 기능은 검사용 컨테이너에서 검증한 상태이며 게임 실행 경로 적용 완료로 주장하지 않는다.

참조 필드 교체 직후 발생한 과거 누락 경고 10건은 Console에 남아 있다. 이후 5개 난이도의 실제 프리팹 참조와 TryValidate 성공을 확인했으며 최종 컴파일 오류는 0건이다. 기존 Console 기록을 지우지 않았다.

EditMode 검증이며 실제 PlayMode 생명주기·빌드·실기기 부하를 검증한 것은 아니다. 성능·Zero-GC 수치는 주장하지 않는다. 외부 서비스·클라우드 설정 변경이 없어 재배포가 필요하지 않다.

## 수동 재현 순서

1. Assets/Prefabs/Enemy의 5개 프리팹을 열고 루트의 StatsConfig와 Body의 SpriteRenderer Sprite를 확인한다.
2. Assets/Configs/Difficulty의 1~5 에셋에서 프리팹과 Max Spawn Count를 확인한다.
3. 분리된 검사용 컨테이너에 EnemyPoolGlue와 EnemySpawnGlue를 등록한다. 이는 기존 CombatCompositionRoot 변경 지시가 아니다.
4. Configure 후 TrySpawn으로 상한만큼 요청하면 성공하고 추가 요청은 false다. 반환은 TryDespawn으로 한다.
5. 반환 전 State를 보관하고 피해를 준 다음 재대여한다. 오브젝트는 같고 State 참조는 다르며 체력은 StatsConfig 기본값이다.
6. 스폰 담당 Dispose 후 풀 Dispose로 소유 객체를 정리한다. 테스트에서 만든 임시 씬을 저장하지 않는다.
